# Git·GitHub 개발 규칙

이 문서는 `pioneer-1st-code-team07`의 이슈·브랜치·커밋·PR·출시 관리 기준을 정리한다.

## 1. 적용 범위와 저장소 기준

- 저장소: `NH-Futures-Pioneer-1-Team07/pioneer-1st-code-team07`
- Git은 프로젝트 루트의 `.git` 하나로 관리한다.
- 프론트엔드·백엔드 등 영역을 구분할 필요가 생기면 아래의 FE·BE 표기를 적용한다.
- API 키·토큰·비밀 설정은 커밋하지 않는다.
- 필요한 환경 변수의 이름과 예시는 비밀값을 제거한 `.env.example`로 관리할 수 있다.

운영 기준은 `dev`를 기본·통합 브랜치로 사용하고 `main`에서 검증한 출시 버전을 관리하는 것이다. 

## 2. 이슈 작성과 메타데이터

### 이슈·PR 공통 작성 원칙

이슈·PR은 대화를 모르는 팀원도 작업 내용과 결과를 파악할 수 있게 작성한다.

- 이슈에는 이번에 할 작업과 기대 결과를 쓴다.
- PR에는 실제 변경한 내용과 확인한 결과를 쓴다.
- 작업 항목에는 구체적인 대상과 수행 내용을 명시한다.
- 조건·범위·상태에 따라 의미가 달라지면 해당 조건·범위·상태를 명시한다.
- 작업 판단에 도움이 없는 대화 이력·반복 문구·작업 과정 나열은 생략한다.

### 작업 범위 확인과 생성 승인

AI 에이전트에 이슈 생성을 요청할 때는 초안 작성 전에 다음 항목을 파악한다.

- 목적: 해결할 문제 또는 얻으려는 결과
- 수행 내용: 이번 이슈에서 할 구체적인 작업

진행 순서:

1. 기존 대화와 관련 문서에서 확인한 내용을 짧게 요약해 사용자에게 보여준다.
2. 범위·기대 결과·완료 기준이 모호하면 가능한 해석이나 선택지를 제시해 질문한다.
3. 확인한 목적·작업 대상·수행 내용·완료 기준으로 제목·본문 전체 초안을 작성한다.
4. 전체 초안에 대한 별도 명시적 승인을 받은 뒤 이슈를 생성한다.

- 요청이 명확하면 작업 요약과 전체 초안을 함께 제시한다.
- 이미 사용자가 지정하거나 확인한 내용은 반복해서 질문하지 않는다.
- 이미 승인된 동일 초안은 다시 승인받지 않는다.
- PR 생성에도 제목·본문 전체 초안을 먼저 보여주고 별도 명시적 승인을 받는 절차를 적용한다.
- AI 에이전트는 브랜치 생성·커밋·push를 사용자가 요청하거나 승인한 범위에서 수행한다.
- AI 에이전트의 PR 병합·출시·배포는 명시적 요청이 있을 때만 실행한다.

### 이슈 본문 작성

- [작업 요청 템플릿](../.github/ISSUE_TEMPLATE/task.md)을 사용한다.
- 목적에는 해결할 문제와 기대하는 결과를 짧게 쓴다.
- 작업 범위에는 정한 이번 작업을 항목별로 쓴다.
- 완료 조건에는 확인 가능한 결과와 확인 방법을 체크리스트로 쓴다.
- 조사·설계 작업이면 확인할 질문과 남길 결과물 또는 결정할 사항을 구체적으로 쓴다.
- 작업 범위를 넓히려면 사용자와 논의해 정한다.
- 담당자는 실제 작업 담당 팀원으로 지정한다.

### 제목·라벨

이슈 제목에는 자신의 이슈 번호를 중복 작성하지 않는다.

| 작업 | 유형·영역 표기 |
|---|---|
| 프론트엔드 구현 | 작업 유형과 `[FE]` |
| 백엔드 구현 | 작업 유형과 `[BE]` |
| 프론트엔드·백엔드 함께 변경 | 작업 유형과 `[FE/BE]` |
| 문서·CI 등 영역 구분이 필요 없는 작업 | 작업 유형만 표시 |

제목 형식:

```text
유형: 작업 설명
유형: [FE] 작업 설명
유형: [BE] 작업 설명
유형: [FE/BE] 작업 설명
```

예시:

```text
feat: [FE] 목록 조회 화면 구현
feat: [BE] 목록 조회 API 구현
feat: [FE/BE] 목록 조회 기능 구현
design: 주요 화면 UI/UX 프로토타입 설계
docs: Git·GitHub 개발 규칙 정리
```

다음은 작업 유형별 권장 라벨 이름이다. 실제 저장소에 있는 라벨을 확인한 뒤 적용하며, 없는 라벨은 팀이 이름과 사용 범위를 정해 별도로 생성한다.

| 작업 | 권장 라벨 이름 |
|---|---|
| 기능 구현 | `✨ Feature` |
| 버그 수정 | `🚨 Fix` |
| 제품 UI/UX·프로토타입 설계 | `🎨 Design` |
| 문서 | `📝 Docs` |
| 테스트 | `🧪 Test` |
| 코드 구조 개선 | `♻️ Refactor` |
| 기타 관리 | `🔧 Chore` |
| CI 설정 변경 | `⚙️ CI` |
| 출시·배포 | `🔖 Release` |

## 3. 이슈·브랜치·PR 연결

이슈 생성 → 연결된 작업 브랜치 생성 → `dev` 대상 PR 생성 → 병합 후 이슈 종료 순서로 진행한다.

- 새 작업 브랜치는 최신 `dev`를 기준으로 생성한다.
- GitHub Development 연결은 이슈의 Create a branch 또는 GitHub CLI의 이슈 브랜치 생성 기능으로 등록한다.
- 이슈를 완료하는 작업 PR에는 `Closes #42`처럼 종료 키워드를 작성한다.
- GitHub의 기본 브랜치가 `dev`로 설정되어 있으면, 종료 키워드를 포함한 작업 PR을 `dev`에 병합할 때 해당 이슈가 자동 종료된다.
- 이슈를 참고만 하는 PR에는 `Refs #42`를 사용한다.

종료 키워드의 동작 조건은 [GitHub의 이슈·PR 연결 문서](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)를 따른다.

GitHub CLI 사용 시 브랜치 생성 예시:

```bash
gh issue develop 42 --repo NH-Futures-Pioneer-1-Team07/pioneer-1st-code-team07 --base dev --name feat/42-fe-list --checkout
```

## 4. 브랜치 전략

`dev`에서 작업을 통합하고 `main`에서 출시 버전을 관리한다.

- 팀의 기본·통합 브랜치는 공통 `dev`를 사용한다.
- 일반 작업은 최신 `dev`에서 브랜치를 생성한다.
- Git 브랜치는 저장소 전체 상태를 가진다.
- 작업 브랜치가 병합되면 해당 브랜치를 삭제한다.
- 후속 수정이 필요하면 최신 `dev`에서 새 브랜치를 생성한다.

| 브랜치 | 역할 | 유지 |
|---|---|---|
| `main` | 검증한 출시 버전 관리 | 상시 |
| `dev` | 완료한 기능·수정 통합 및 검증 | 상시 |
| `feat/*` | 새로운 기능 구현 | 작업 완료 후 삭제 |
| `fix/*` | 버그 수정 | 작업 완료 후 삭제 |
| `design/*` | 제품 UI/UX·프로토타입 설계 | 작업 완료 후 삭제 |
| `docs/*` | 문서 변경 | 작업 완료 후 삭제 |
| `test/*` | 테스트 변경 | 작업 완료 후 삭제 |
| `refactor/*` | 기능을 유지하는 코드 구조 개선 | 작업 완료 후 삭제 |
| `chore/*` | 기타 관리 작업 | 작업 완료 후 삭제 |
| `ci/*` | CI 설정 변경 | 작업 완료 후 삭제 |
| `release/*` | 출시 준비와 다음 개발의 분리가 필요할 때 도입 검토 | 도입 시 별도 결정 |

## 5. 작업 브랜치 이름

- 작업 브랜치 유형은 `feat`, `fix`, `design`, `docs`, `test`, `refactor`, `chore`, `ci`를 사용한다.
- `init`은 최초 초기화 커밋에만 사용한다.
- 브랜치에서는 소문자 `fe`, `be`를 사용한다.
- 이슈 번호에는 `#`를 붙이지 않는다.
- 작업 설명은 소문자 영문과 하이픈으로 작성한다.
- FE·BE를 함께 구현하거나 영역 구분이 필요 없는 작업은 영역 표시를 생략한다.
- 디자인 작업은 영역 표시를 생략한다.

기본 형식:

```text
유형/이슈번호-작업설명
유형/이슈번호-fe-작업설명
유형/이슈번호-be-작업설명
```

예시:

```text
feat/42-fe-list
feat/42-be-list
feat/42-list
fix/43-be-list-sort
design/44-ui-ux-prototype
docs/45-github-workflow
ci/46-checks
```

## 6. 커밋 형식

Conventional Commits를 사용하며 범위(scope)는 생략한다.

- 작업 브랜치의 개별 커밋에서는 이슈 번호를 생략한다.
- FE·BE 작업의 커밋에서는 해당 영역을 표시한다.
- 문서·관리 등 영역 구분이 필요 없는 작업에서는 영역 표시를 생략한다.
- 디자인 작업의 커밋에는 `design:` 유형을 사용하고 영역 표시를 생략한다.
- 디자인의 실제 프론트엔드 구현 커밋에는 `feat: [FE]`를 사용한다.
- 커밋 유형은 실제 변경 내용에 따라 선택한다.
- `init`은 저장소 최초 초기화에만 사용하며, 이미 초기화된 저장소에 다시 사용하지 않는다.

기본 형식:

```text
유형: 변경 설명
유형: [FE] 변경 설명
유형: [BE] 변경 설명
유형: [FE/BE] 변경 설명
```

예시:

```text
feat: [BE] 목록 조회 API 구현
feat: [FE] 목록 테이블 추가
fix: [BE] 목록 날짜 정렬 수정
design: 주요 화면 UI/UX 프로토타입 설계
test: [BE] 목록 페이지네이션 검증
docs: GitHub 개발 규칙 정리
```

| 유형 | 사용 |
|---|---|
| `init` | 저장소 최초 초기화 커밋 |
| `release` | 검증한 버전 출시 |
| `feat` | 새로운 기능 |
| `fix` | 버그 수정 |
| `design` | 제품 UI/UX·프로토타입 설계 |
| `docs` | 문서 변경 |
| `test` | 테스트 변경 |
| `refactor` | 기능을 유지하는 코드 구조 개선 |
| `chore` | 기타 관리 작업 |
| `ci` | CI 설정 변경 |

## 7. 작업 PR

- [PR 템플릿](../.github/pull_request_template.md)을 사용한다.
- 본문은 2절의 공통 작성 원칙과 생성 승인 절차를 따른다.
- 작업 PR은 `dev`를 대상으로 생성한다.
- 하나의 PR은 하나의 논리적 작업으로 정리한다.
- 제목의 유형·영역 표기는 2절의 작업별 제목 표를 따른다.
- 실제 변경 내용과 변경 후 동작 또는 결과를 쓴다.
- 라벨은 실제 저장소의 라벨을 확인하고 2절의 작업 유형에 맞춰 지정한다.

제목 형식:

```text
유형: 작업 설명 (#이슈번호)
유형: [FE] 작업 설명 (#이슈번호)
유형: [BE] 작업 설명 (#이슈번호)
유형: [FE/BE] 작업 설명 (#이슈번호)
```

예시:

```text
feat: [FE] 목록 조회 화면 구현 (#42)
feat: [BE] 목록 조회 API 구현 (#42)
fix: [BE] 목록 날짜 정렬 수정 (#43)
design: 주요 화면 UI/UX 프로토타입 설계 (#44)
docs: GitHub 개발 규칙 정리 (#45)
```

## 8. 머지 규칙

- `dev`의 스쿼시 커밋 메시지는 작업 PR 제목과 동일하게 작성한다.
- 출시 PR 제목과 `main`의 스쿼시 커밋 메시지는 `release: v0.1.0 출시`처럼 작성한다.
- 출시 후 `main`을 `dev`에 반영할 때는 일반 Merge를 사용한다. 다음 출시 PR의 커밋 비교와 병합 기준을 연결하기 위한 절차다.
- `main`에는 최초 초기화 기록을 제외하면 출시 단위 변경 기록을 남긴다.
- 출시 준비와 다음 기능 개발을 동시에 진행해야 할 때 `release/*` 도입을 검토한다.

| 방향 | 방식 | 결과 |
|---|---|---|
| 작업 브랜치 → `dev` | Squash merge | 작업 단위 커밋 하나 |
| `dev` → `main` | Squash merge | 출시 단위 커밋 하나 |
| 출시 후 `main` → `dev` | 일반 Merge | 출시 이력 및 커밋 관계 동기화 |

작업 흐름:

```text
이슈 생성
  → 최신 dev에서 작업 브랜치 생성
  → 개발·커밋
  → PR·리뷰·검증
  → dev에 Squash merge
  → 작업 브랜치 삭제
```

출시 흐름:

```text
출시할 변경 검증
  → dev에서 main으로 출시 PR
  → main에 Squash merge
  → 병합한 커밋 검증
  → 버전 태그와 출시 기록 작성
  → main을 dev에 일반 Merge
```
